## The three corrections that shaped the design

Recorded because each one invalidated something previously believed true.

1. **Setup-tokens cannot read usage.** `claude setup-token` mints an
   inference-only credential (`user:inference`, no `user:profile`), so
   `/api/oauth/usage` returns **403**. The original spike validated the endpoint
   with a full-scope *session* token and never tested the credential type the
   tool actually used. Fixed by capturing the login credential instead.

2. **Falling back to the probe on 403 was rejected deliberately.** A probe *is*
   an inference request, so it opens a five-hour window. Auto-probing on every
   status check would open windows on all four accounts and destroy the
   staggering the tool exists to provide. 403 must stay a hard, explained error.

3. **`HOME` overrides break Keychain access.** `security` resolves the login
   keychain through `$HOME`, so sandboxing a test with `HOME=$(mktemp -d)`
   produces a false "no Claude Code login found". Any future test that touches
   the Keychain must use the real `HOME`.

## The discovery that should drive the next session

**`CLAUDE_CONFIG_DIR` gives each profile its own independent auth slot.**

Verified: with `CLAUDE_CONFIG_DIR=/tmp/x`, `claude auth status` reports
`loggedIn: false` while the default profile is logged in. The Keychain shows the
mechanism — a second entry named `Claude Code-credentials-8b5c90b4` alongside the
default `Claude Code-credentials`. The suffix is derived from the config dir.

This matters because **`claude auth login` currently overwrites the single
default credential**. Logging into subscription #2 destroys #1's credential. The
tool survives that today only because `cuw add` takes a *copy* — but re-adding
or repairing an account then requires logging in again.

With per-account config dirs, all four logins coexist permanently.

## Plan for next session

### Phase 1 — Get all four subscriptions registered (highest value)

The logins are inherently serial: each is an interactive browser flow, one at a
time. This is the only manual work left, and it is one-time.

Current flow, repeated per subscription:

```
claude auth login          # browser opens; sign in as that subscription
cuw add <name>             # captures the credential it just stored
```

Suggested ids: `superclaude` (done), plus three more matching the accounts.

**Before starting:** `claude auth login` replaces the active session in that
terminal. Use a separate terminal from any live work.

### Phase 2 — Profile-isolated accounts (the real fix)

Implement `cuw login <id>`, which:

1. Creates `~/.config/cuw/profiles/<id>/`
2. Runs `CLAUDE_CONFIG_DIR=<that dir> claude auth login`, so the credential lands
   in its **own** Keychain slot and never collides with the default login
3. Reads back `CLAUDE_CONFIG_DIR=<dir> claude auth status --json` to capture the
   account email automatically
4. Registers the account

Benefits: your default `claude` login is never disturbed; each account can be
re-authenticated independently; `cuw prime <id>` can reuse the same profile dir
it already isolates into.

Open question to resolve first: whether `cuw` should keep copying the credential
into `cuw-token/<id>` (current design, self-refreshing) or read the profile's
Keychain slot directly and let `claude` own refresh. Copying is already built and
tested; reading directly removes duplication but couples `cuw` to an internal
naming scheme (`Claude Code-credentials-<hash>`) that could change. **Recommend
keeping the copy** and using profiles only for login isolation.

### Phase 3 — Polish

- Populate `label`/`email` from `claude auth status --json` instead of leaving
  `email` empty (`src/commands/add.ts` writes `email: ''` today, deliberately).
- Run `cuw doctor` and `cuw rm` against real accounts — neither has ever been
  executed outside unit tests.
- Exercise `cuw prime --cold` once a genuinely cold account exists.
- Consider a `--watch` mode; `cuw status --json` already supports a statusline.

## Gotchas for whoever picks this up

- **Never** auto-fall back to the probe path for routine status reads. See
  correction #2.
- Tokens may appear only in `keychain.ts`, `credentials.ts`, `token-source.ts`,
  `usage-probe.ts`, `prime.ts`, and `cli.ts`. Never in render, JSON, or log
  paths. `prime.ts` has a `redact()` helper for stderr tails.
- The test fixture `tests/fixtures/usage-api.json` is **synthetic** (year-2099
  timestamps, USD, zeroed amounts) because the repo is public. Do not replace it
  with a live capture — the original contained real billing figures, and an
  earlier commit had to be discarded from history to remove them.
- Git history was intentionally rebuilt as a single root commit to strip those
  figures. Do not restore the old history.
- Run `bunx tsc --noEmit` as well as `bun test`; a tests-only loop missed nine
  strict-mode errors, including a `sort()[0]` that could return `undefined`.
